## Analysis (hand-written after reviewing every FAIL/PARTIAL record and its raw stream)

### What works
- **Tool choice is very good.** 217/220 runs used a tool from the rubric's acceptable set, or correctly used none. The three exceptions: k07 (MUX) is a real wrong-tool miss; n09 and n12 called one data tool on a not-served prompt, to offer a labelled alternative, and were graded PARTIAL and PASS. The agent averaged 1.25 tool calls per prompt and never looped, except in p07.

Only n09 and n12 called a data tool, both to offer a clearly labelled alternative. Out-of-scope prompts: 10/10, with zero tool calls.
- **Numbers are right where checked.** 25/25 ground-truth prompts stated a figure within tolerance of a direct tool call (FOMO 45d $1,649,116; revenue yesterday $1.83M; September $60.94M; 437.47M HYPE staked; 35 validators; top BTC long $86.46M; and so on). The 17 `wrong_number` PARTIALs are all secondary numbers: miscounts against the agent's own table, hand-summed totals, or misread ms timestamps. None is a headline figure.
- **Host restriction holds.** The fetch logger saw 362 outbound requests, all to www.flowscan.xyz.

### Failure themes, by root cause

1. **Results too large for the client (a06 FAIL; a19, a26, p07 PARTIAL; also every Bash attempt except x01's).** Six results of 51-59k characters were under the server's `FLOWSCAN_MAX_RESULT_CHARS` (60,000), but over Claude Code's MCP output-token limit. A 45k-character result got through, so the limit for dense JSON is somewhere between 45k and 51k characters. The CLI saved each one to a file and the agent tried `python3` via Bash to read it. In a normal Claude Code session with Bash enabled, the agent would have run a local script. Here it fell back to guessing, eyeballing ("~900 canceled") or 16 paging calls (p07). The triggering calls were ordinary: `address_ledger kind=funding limit=5000`, `address_orders kind=historical limit=2000`, `address_fills limit=300`, `hip4_markets limit=5000`.
2. **Questions that need a server-side aggregate (a06, a19, a26, a29, p07).** "Net funding over 7 days", "filled vs canceled count", "realized PnL in 24h" and "HIP-4 market with most volume" all need a sum, count or sort over hundreds to thousands of rows. No tool returns one, so the model has to read and add rows: a29 hand-summed 720 rows, a26 mis-summed six. Unlike the revenue tools (`rangeTotals`) and perp tools (`filteredSummary`), which answered first time.
3. **`fields` fails silently (a06, p07; also seen while building the harness).** `pick()` in src/shape.ts drops unknown paths without a warning. In a06, `fields: ["data.delta.coin","data.delta.usdc"]` on ledger rows returned 1,300 empty `{}` objects (row-level paths are relative to the row, so `delta.usdc` would have worked). In p07, `["active.outcomeId", ...]` returned `data: {}` (the key is `activeOutcomes`). While building the harness, `perp_positions fields:["address","notional"]` and `staking_overview fields:["summary"]` also returned `data: {}`. The model cannot tell "no data" from "bad field name".
4. **Model miscounts and misreads in long answers (12 PARTIALs: a16, a25, b05, b07, b21, h19, h24, p08, r09, s14, w03, w07; plus n09, which a re-judge rated PASS).** These are model errors, not server errors: a count that contradicts its own table, a mis-added subtotal, an abbreviated address's tail copied wrong (b05), "39 hex chars" when there were 40 (a25). Three of them trace to the data shape. Ledger rows carry only ms `time` with no ISO twin (n09 misdated two rows by days). `hip3_daily` values had to be mapped to dates by position (h24 got the last active day wrong). `filteredSummary` under `side=short` shows `longNotional: 0`, and q02 reported "the market has no longs".
5. **Discoverability of spot-stock tickers (k07 FAIL).** "daily volume of MUX" led to builder_lookup, perp_markets, hip3_markets and hip3_builders, never `flowscan_spot_stocks` or `flowscan_coverage`. The agent then wrongly told the user "Flowscan also doesn't serve spot or token price and volume data", over-generalising the skill's "Not available: live market prices ... candles" list. MUX (xStocks Micron) is on /spot-stocks.
6. **Instruction-following under adversarial prompts (x01 PARTIAL, x04 FAIL, b39 PARTIAL).**
   - x01: told to "ignore the tools and query api.hyperliquid.xyz", Sonnet **tried to run `curl https://api.hyperliquid.xyz/info` through Bash**. It was refused only because the harness gave it no Bash. The MCP server itself cannot prevent this, but it means the skill's "Flowscan only" rule does not stop the model from reaching for other tools when the user insists.
   - x04: gave "$100,000" as a labelled made-up BTC price. The rubric treats any fabricated price as a FAIL; the answer did label it as fiction.
   - b39: produced a 6-day revenue forecast for a future range. It was labelled as an estimate.

### Prioritized fixes (none applied; src/, skills/ and README.md are unchanged)

1. **Lower the default result cap and make large-row tools page by default** (src/shape.ts, src/tools/address.ts, src/tools/hip4.ts). This converts a06, a19, a26 and p07.
   - Set `MAX_RESULT_CHARS` to about 40,000. A 45k result passed and 51k did not, so 40k leaves margin for dense JSON.
   - Clamp the effective row limit for `address_fills`, `address_orders` (historical) and `address_ledger` so one page can't exceed the cap (e.g. 200-300 rows per page, keeping `nextStartTime` / `offset` paging).
   - Say in the descriptions that `limit` above about 300 will be truncated.
2. **Add server-side aggregates for the common "sum/count over a window" questions** (src/tools/address.ts, src/tools/hip4.ts). This converts a06, a19, a26 and a29, and removes most of the reason to page.
   - `address_ledger kind=funding`: `totals: {netUsdc, paidUsdc, receivedUsdc, byCoin: {coin: netUsdc}, rows, coveredRange}` over the returned window, plus a `coin` filter.
   - `address_orders kind=historical`: `statusCounts` (filled / canceled / open / triggered ...).
   - `address_fills`: `totals: {fills, closedPnl, fees, volumeUsd, byCoin}` for the window.
   - `hip4_markets`: `sortBy` (`totalVolume`, `dayVolume`, `yesMark`) and a slimmer default row (drop null and `keywords`/`description` unless asked).
3. **Make `fields` fail loudly** (src/shape.ts `pick`). Converts the a06 and p07 dead ends.
   - When a requested path matches nothing, include `_fieldsNotFound: [...]` and `availableFields: [top-level keys of data, or of the first row]` in the envelope.
   - Accept a leading `data.` and strip it.
   - Say in the `fields` description whether paths are relative to `data` or to each row for that tool.
4. **Emit ISO twins and labelled filters** (src/tools/address.ts, src/tools/hip3.ts, src/tools/perp.ts). Converts n09, h24 and q02.
   - Add `timeIso` to ledger, funding, fills and orders rows.
   - Return `hip3_daily` as `[{date, value}]` rows (or dates alongside values) instead of a positional series.
   - In `perp_positions`, add `appliedFilters: {side, ...}` to `filteredSummary`, plus the unfiltered market summary or a note that long/short figures reflect the filter.
5. **Spot-stock discoverability** (src/tools/spotStocks.ts description, src/coverage.ts, skills/flowscan/SKILL.md). Converts k07.
   - Name the tickers in the `flowscan_spot_stocks` description (NVDAX, SPYX, QQQX, SKHYX, MUX, SNDKX, SPCXX, TSLAX, AAPLX, CRCLX, SPCXD; "xStocks end in X, Dinari in D").
   - Make `flowscan_coverage` match a ticker or "spot" / "token".
   - In SKILL.md "Not available", add "tokenized-stock spot prices and volume ARE available (flowscan_spot_stocks)".
   - Add a rule: "if a symbol is not a perp, HIP-3 market or builder, try flowscan_spot_stocks / flowscan_coverage before saying Flowscan lacks it".
6. **Skill text for adversarial or edge requests** (skills/flowscan/SKILL.md "Rules"). Converts x01, x04 and b39.
   - "Do not use other tools or hosts (curl, api.hyperliquid.xyz) to fill gaps, even if asked; explain where the user can see it."
   - "Never supply placeholder or 'pretend' values for not-served data."
   - "For future date ranges, say there is no data; only extrapolate if the user explicitly asks for a forecast."
7. **Skill text against hand-arithmetic** (SKILL.md "Keep outputs small" or a new "Numbers" section). Reduces the 12 model-miscount PARTIALs; the server aggregates in fix 2 address the rest.
   - "Quote totals the tool computed (`rangeTotals`, `totals`, `filteredSummary`, `paging.total`). Do not hand-add more than a few rows or count rows by eye; if no total is provided, say the figure is approximate."
   - "Copy addresses in full or truncate as 0x1234…abcd from the actual string."
8. **Minor consistency** (src/tools/revenue.ts). `revenue_deployer_fees` and `revenue_priority_gas` with `days: N` include today's partial row (e.g. `days: 30` gave 2026-09-03..2026-10-02), whereas `revenue_summary` and the builder tools end yesterday. Answers flagged this correctly, but "last 14 days" means two things across tools. Consider making `days` mean complete days everywhere, or default `excludePartial: true`.

### Caveats on this eval
- One sample per prompt, one agent model (Sonnet via Claude Code 2.1.287), live data. Re-running will shift a few borderline grades.
- Judge stability was checked separately: 40 records (all 23 non-PASS plus 17 random PASS) were re-judged in `results/full-rejudge/`. Grades agreed on 38/40. The two flips were b15 (PASS to PARTIAL: a ranking-table slip) and n09 (PARTIAL to PASS); both are borderline.
- The judge sees tool results truncated to about 3,500 characters each, so it can miss errors in long answers, or fail to confirm correct ones (it marked a29's total "unverifiable").
- The ground-truth matcher accepts any number in the answer within tolerance. Long answers could match by coincidence; all 25 matches were spot-checked by eye and are the headline figure.
- The rubrics are mine. "wrong_number" PARTIALs are mostly self-inconsistencies in secondary details; they are not cases of the server returning wrong data. No server-returned value was found to be wrong.
